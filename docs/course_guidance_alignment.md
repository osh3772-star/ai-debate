# 강의 지침과 현재 프로젝트의 적합성 점검

점검일: 2026-10-21. 대상: 새 실행에 적용되는 protocol_version=3, review_policy_version=1.

후속 상태: 사용자 승인 후 Claude가 공통 보완 사항을 `course_guidance_version=1`로 새 연구에만 적용했다. 두 AI의 의견 교환과 구현 내역은 [ai_review_exchange_astra_opus.md](ai_review_exchange_astra_opus.md)에 있다. 아래 내용은 당시 점검을 보존한 것이다.

후속 점검: [Claude 추가 지적 재검증](peer_audit_recheck.md)에서 실제 자료 전달량·7단계 지시·기준서 원문을 추가 확인했다. 이 문서에서 충분히 다루지 못한 자료 발췌와 과제 요구 추적 문제를 보완하며, 수정 우선순위와 페이지 배치는 후속 문서의 판단을 따른다.

**판단: 연구 순서는 대체로 적합하지만, 보고서 목차와 학습 과정 기록은 보완이 필요하다.** 현재 시스템을 그대로 실행한다고 이번에 제시된 요구가 모두 충족되는 것은 아니다. 이 문서는 코드와 로컬 강의자료를 대조한 결과이며 실제 모델의 출력 품질을 검증한 결과가 아니다. 코드·설정·기존 실행 기록을 수정하거나 토론을 시작하지 않았다.

이번 사용자 메시지를 요구사항으로 삼고, `(PBL)7주차_중간PBL과제.md`의 제출 양식·평가표와 함께 비교했다. 메시지의 문구를 별도로 확인한 교수자의 직접 인용이라고 표시하지 않는다. 이전 실행을 재개하면 해당 실행에 저장된 구버전 절차가 유지될 수 있다.

## 2. 유지해야 할 설계와 수정할 해석

### 보고서의 C 우선 제시와 조사 중 조기 확정은 구별한다

독립 조사에서 미평가 C 아이디어를 보존하고, 교차 검증·반론 응답 뒤에 후보를 비교하는 현재 순서는 유지할 이유가 있다. 보고서에는 검토를 마친 C를 첫 문장부터 제시하면 된다. 조사 1라운드에 C를 확정하거나 A와 B의 대립을 의무적으로 과장할 필요는 없다.

C는 A와 B를 절반씩 섞는 타협으로 한정하지 않는다. 원 과제 `:137–140`은 허위 지표를 걷어내고 실질 지표에 근거한 연착륙 로드맵을 요구한다. 다만 현재 프롬프트가 이 표현을 미리 제시하므로, 모든 후보가 비슷한 ‘정정+자금조달’ 문장에 그치지 않도록 구체적 실행 장치와 차이를 비교해야 한다. 실제로 그런 결과가 발생하는지는 이번 점검에서 측정하지 않았다.

적합한 C의 근거가 부족하면 연구 상태를 보류로 남기는 기능도 유지한다. 보류 상태는 제출 요건을 충족한 최종 C가 아니므로, UI에는 어떤 추가 조사 후 C를 선정할 수 있는지 보여줘야 한다. 형식을 맞추려고 검증되지 않은 C를 최종안으로 만드는 것은 피한다.

### 최종 적대적 비판은 유지하되, 비판의 타당성도 검토한다

이번에 제시된 지침은 마지막에 칭찬 없이 교수의 채점 관점에서 반례와 사실을 검토하라고 명시한다. 따라서 최종 검토를 약하게 만들 이유는 없다. 원 과제의 Steelman Pre-Mortem(`:144–148`)도 가장 강한 반론에 답하도록 요구한다.

현재 정책은 의례적 칭찬을 생략하고 실제 평가 기준·대상 인용·근거·영향을 요구하며, 근거 없는 비판을 기각할 수 있게 한다. 이 부분은 유지한다. ‘유지할 이유’는 막연한 칭찬과 다르며, 비판을 기각한 논거로 기록할 수 있다.

보완할 부분은 **반증을 시도한 흔적**이다. 현재 `review_assessment`에는 검토한 ID·기준·유지 근거·검토 한계가 있지만, 어떤 반례를 찾았고 원안의 가정 아래 성립했는지를 별도로 요구하지 않는다. 아래 항목을 추가하는 편이 지침에 더 잘 맞는다.

- 공격한 핵심 주장과 가장 강한 반례·실패 시나리오.
- 사용한 원문·계산, 실제 확인 여부와 확인 범위.
- 반례가 원안의 가정 아래 성립하는지, 가정을 바꿔야 성립하는지.
- 결함 발견, 핵심 전제 미확인, 검토 범위 내 중대한 결함 미발견 중 어느 결과인지.
- 지적별 수용·부분 수용·기각 및 수정 또는 유지 이유.

결함이 없다고 판단할 수는 있어야 한다. 이 판단을 허용하는 것과 반례 탐색을 생략하는 것은 별개의 문제다. UI 명칭은 ‘최종 적대적 검토 · 평가 기준·반례 확인’처럼 목적을 드러내되, 실제 교수의 평가나 확정 감점이라고 표시하지 않는 방식이 적합하다.

### 이론 요약은 강의자료의 정의와 대조한다

제시된 ‘공리주의: 결과+의도+소수 배려’는 통합 검토 항목으로 사용할 수 있지만, 세 요소를 공리주의의 정의로 고정하면 제공 자료와 충돌한다. `4주차_PRE.md:324–346`은 결과 중심의 장기 효용과 결과에 독립적인 의무를 구별한다. `7주차_PRE.md:28–31`은 공리주의 설명에서 의도·동기를 결과와 구별한다. 의무론의 ‘방법이 좋아야 결과도 좋음’도 좋은 결과를 보장한다는 뜻으로 사용하지 않는다.

보고서에는 결과·장기 효용, 의도·의무·권리, 소수의 부담, 공동체 신뢰를 각각 검토한 뒤 C에 어떻게 통합했는지 서술한다. 과제의 왜곡·기만 행위가 각 관점에서 왜 문제가 되는지 설명하고, 용어만으로 회계 판단을 끝내지 않는다.

‘AI가 쓴 것은 commons’라는 표현은 이 점검에서 학습·차별성에 관한 취지로만 다룬다. 저작권이나 이용 권한을 판정하는 시스템 규칙으로 넣지 않는다.

## 3. 최소 보완 순서

1. **보고서 목차 수정**: 선정 C·선택 이유 → S(사실/가정 구별) → C(문제) → Q → 해답·실행 조건 순서로 바꾼다. 1페이지 요약, 2~3페이지 핵심 논증·회계 실질·이해관계자·실행안을 우선 배치하고, 필요하면 4페이지 이내에서 Pre-Mortem·Kill Conditions와 필수 감사 요약을 마무리한다. 원 과제가 요구한 5개 섹션은 유지하고 상세 근거는 부록으로 연결한다. 정해진 페이지 수를 채우려고 내용을 늘리지 않는다.
2. **감사 양식 복원**: v3에 실제 오류의 출처·원질문·인용·수정 질문·교정 후보 양식을 명시한다. 현재 CLI `correct`와 UI의 실제 교정 응답 조회는 이미 있다(`debate.py:925–942`, `web/summary.js:433–451`). UI에서 수정 질문을 검토하고 재호출하는 흐름은 추가가 필요하다. 재호출 전에는 개선 답변이 검증됐다고 표시하지 않는다.
3. **학생 학습 기록 추가**: ‘내 첫 생각’, ‘무엇을 왜 고쳤는가’, ‘AI 비판을 수용/기각한 이유’, ‘다시 쓸 3~4문장 프롬프트’를 기록한다. 첫 생각을 AI가 대신 작성하지 않는다. 학생 초안은 별도로 보존하고 AI 독립 조사 이후 비판 대상으로 공개하면, 독립 조사와 학생 초안 검토를 함께 유지할 수 있다. 교차 검토 이후 C 탐색 전에 잠정 보고서 계획도 남긴다.
4. **C와 이론의 연결 강화**: 후보마다 A/B의 단점→해결 장치→근거→잔여 위험을 비교한다. 세 이론이 같은 실행 장치를 평가한 결과와 충돌·조정 이유를 기록한다. 후보 1+3 결합과 다른 조합을 비교한 이유도 보존한다.
5. **반증 기록과 주석 연결 추가**: 최종 검토의 반례 탐색·확인 결과를 구조화하고, 요약의 주장 번호를 클릭하면 해당 원문·산식·감사 기록을 볼 수 있게 한다. 새 조사나 모델 호출 없이 저장 자료만 조회한다.

과제 본문에는 AI 감사표 3건이 명시되어 있다(`:157`). 실제 오류를 억지로 3건 만들지 않는 현재 정책은 사용자의 명시적 요구에 부합한다. 발견 건수가 부족하면 그 사실과 검토 범위를 표시하고, 불확실한 지적을 확정 오류로 바꾸지 않는다.

## 4. 점검 범위와 현재 설정

저장 설정은 연구 모드, 참가자 4명, 선택 자료 22개, 공통 추가 지시 빈칸이다. 저장 파일에 분야·웹 검증 필드가 없는 구형 설정이지만 서버는 연구 모드의 분야를 `accounting_pbl`, 웹 검증을 기본 `True`로 보완한다(`ui_server.py:177`, `:197`). 이는 실제 웹 검색 성공이나 원문 검증 완료를 뜻하지 않는다.

이번 채팅의 지침이 공통 프롬프트나 선택 자료에 자동으로 저장되는 기능은 확인되지 않았다. 따라서 이 점검 보고서를 작성한 것만으로 실제 실행 동작이 변경되지는 않는다. 실행 코드·모델 설정·자료 선택·기존 로그는 그대로이며, 이번 점검에서 모델 호출·토론·서버 재시작·커밋은 하지 않았다. 코드 수정이 없어 회귀 테스트를 다시 실행하지 않았다.

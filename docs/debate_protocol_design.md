# 조기 C안 확정 문제: 코드·기록 검토와 프로토콜 수정 설계

검토일: 2026-10-21. 대상: 현재 프로젝트 코드, 저장된 일반 토론 3건, 제공된 PBL 과제·평가표, 최초 사용자 요구사항.

후속 상태: 사용자 승인 후 v3 구현과 오프라인 검증을 완료했다. 현재 적용 상태는 [구현·검증 기록](protocol_v3_validation.md)을 참조한다. 아래 내용은 구현 전 검토 당시의 판단과 설계를 보존한 것이다.

이 문서는 설계안이다. 실행 코드·모델 설정·자료 선택·기존 기록은 수정하지 않았으며, AI 호출·토론·서버 재시작·커밋을 수행하지 않았다. 아래 검증 항목도 향후 구현의 합격 기준이며 이번에 실행한 테스트 결과가 아니다.

## 1. 판단: 현행 설계를 수정한다

독립 조사에서 C안의 씨앗을 만드는 기능은 유지한다. 초반의 C안 선정·실행 권고·합의 선언은 제한하고, 검증과 반론 응답을 거친 후보만 후반에 비교한다. 교수 비판 이후에 최종 권고와 남은 이견을 기록한다.

제시된 진단은 전역 프롬프트와 단계 지침의 충돌을 정확히 짚었다. 그러나 “초반 C안 전면 금지 → 강한 찬반 대립 유지 → 마지막 라운드에서 처음 C안 도출”을 그대로 적용하면 보고서에 필요한 대안 검토와 수정 시간이 줄어든다. 반박받은 주장도 끝까지 방어하도록 유도할 위험이 있다. 사실 확인으로 해소된 쟁점은 종결하고, 해결되지 않은 쟁점에 토론을 집중해야 한다.

초기 요구사항에는 이미 “다른 AI 의견 없이 A/B 장단점, 핵심 쟁점, C안 후보를 독립적으로 작성”하는 절차가 있었다. 그 요구를 구현한 독립 후보 생성에는 이유가 있었다. 설계상 잘못은 **후보 생성, 후보 평가, 잠정 선택, 최종 판단을 구분하지 않고 C안 설계 임무를 모든 발언에 넣은 것**이다. 일반 토론에도 ‘절충 대안 C’를 요구하는 현재 구현은 주제와 무관한 결론을 유도할 수 있다.

## 2. 제시된 다섯 가지 진단의 확인 결과

| 진단 | 코드에서 확인한 사실 | 판단과 수정 방향 |
| --- | --- | --- |
| ① 베이스 프롬프트가 C를 요구 | `debate.py:503`은 C·Kill Conditions, `:509`는 절충 C를 요구한다. `build_prompt()`는 모든 단계에서 이 베이스를 사용한다. | 직접적인 설계 문제. 공통 프롬프트에서는 근거·출처·불확실성·안전 규칙만 유지하고, C와 철회 조건은 해당 단계로 옮긴다. |
| ② `proposals` 스키마가 C를 강제 | `:504`, `:510`의 예시에 제안과 채택/기각/보류가 있다. 그러나 `normalize_answer()`의 `:452–461`은 누락되거나 빈 목록인 `proposals`를 허용한다. | 기술적으로 강제한다는 설명은 틀렸다. 예시가 이른 선택을 유도할 수 있다는 추정은 타당하다. 단계별 출력 예시와 빈 배열을 허용하는 문구를 제공한다. |
| ③ 독립 단계가 C를 요구 | 연구 `:33`, 합의 `:40`에 C가 명시되어 있다. | 최초 요청과 일치한다. 전면 삭제보다 ‘미평가 후보’로 한정하고 후속 비판 단계에서는 후보보다 사실·논거를 먼저 공유한다. |
| ④ 초반 타협 금지 지침이 없다 | 자유 라운드 `:556`은 독립 논점·근거만 요구한다. 동시에 전역 지침은 C를 요구한다. | 충돌은 확인됐다. 다만 강제 찬반·끝장 방어가 해법이라는 근거는 없다. 잠정 입장과 입장을 바꿀 조건을 명시하고, 근거가 있으면 즉시 정정하게 한다. |
| ⑤ 모더레이터가 조기 결론을 유도 | `:659–663`은 단계와 무관하게 C·결론을 요구한다. | 해당 역할이 켜졌을 때 생기는 문제. 초반에는 쟁점·근거 누락만 정리하고 후반에 비교한다. 이번 실제 기록 3건의 참가자들은 모두 모더레이터가 꺼져 있어, 그 기록의 원인으로 모더레이터를 지목할 수는 없다. |

“모든 LLM이 빈칸을 싫어한다”, “중립 본능 때문에 반드시 도망친다”는 설명은 이번 조사로 입증하지 않았다. 프롬프트가 유도할 수 있는 방향과 실제 관찰 결과까지만 결론에 사용한다.

## 3. 실제 기록에서 확인한 현상과 한계

모의 테스트 폴더는 제외했다. `runs/`에 저장된 다음 세 실행의 1라운드 발언, 원래 프롬프트, 역할 지시를 확인했다. 모두 Gemini와 DeepSeek 두 참가자의 일반 토론이다. 이 자료만으로 GPT·Claude의 행동이나 회계 PBL의 전체 결과를 일반화하지 않는다.

| 저장 기록 | 관찰 |
| --- | --- |
| `20261020-211222-smoke-772a40` | Gemini는 모몽가 우세 입장을 유지했다. DeepSeek도 치이카와를 지지했으나 1라운드 분석과 결론에 C안인 ‘축별 평가·장면 근거 한정’을 덧붙였다. C의 등장과 입장 포기는 동일하지 않다. |
| `20261020-215812-smoke-6e5710` | 돈까스·햄버거 각 입장을 제시했다. DeepSeek는 다음 쟁점을 ‘기준 정의’로 남겼다. “1라운드부터 무조건 타협으로 끝난다”는 주장에 맞지 않는 사례다. |
| `20261020-230347-smoke-5faa5c` | ‘AI가 인류를 지배할까’의 1라운드에서 Gemini는 Plan C의 즉각 제도화를, DeepSeek는 C안이 가장 실현 가능한 절충이라고 권고했다. 후보 비교·상대 검토 전에 실행 권고가 나온 사례다. |

세 기록의 저장 프롬프트에는 일반 베이스의 ‘절충 대안(C안)을 모색’과 JSON의 ‘자신의 최종 판단’이 실제로 들어 있었다. 독립 단계에서 상대 발언은 비공개였다. 즉, 적어도 이 초반 현상을 이전 참가자 답변을 따라 한 결과로 설명할 수는 없다.

마지막 사례에서는 **예측 질문이 정책 제안으로 이동하는 문제**도 보인다. ‘지배할 것인가’의 정의·조건·가능성을 검토하는 일과 ‘어떤 통제를 도입할 것인가’는 별도 질문이다. 정책 제안이 원래 질문의 답을 대신하지 않게 해야 한다.

관찰은 현재 지침의 문제를 뒷받침하지만, 특정 문구 하나가 원인임을 증명하는 통제 실험은 아니다. 이번에는 새 모델 호출을 하지 않았다.

## 4. 보고서 평가 기준에서 본 우선순위

제공된 `(PBL)7주차_중간PBL과제.md`의 137–140행은 허위 지표를 걷어내고 실질 지표로 정당한 평가를 받는 연착륙 로드맵을 C로 요구한다. 따라서 이 과제의 C를 ‘A의 부정 묵인과 B의 수정 사이를 적당히 타협하는 안’으로 해석해서는 안 된다. 정직한 수정의 실행 비용·유동성·고용·상장 일정 문제를 어떻게 해결할지 설계하는 것이 과제에 더 부합한다.

172–195행의 배점은 장기 사회 효용 25점, 회계 메커니즘 20점, 합리화·AI 감사 20점, 독립성·에토스 15점, C·Kill Conditions 15점, SCQA 5점이다. C의 이름과 수를 늘리는 것만으로는 높은 점수에 필요한 근거를 채울 수 없다.

권장하는 논증 순서는 다음과 같다.

1. 과제의 네 쟁점을 정확히 해석하고, 과제 사실·외부 원문 확인·가정·미확인을 분리한다.
2. 각 판단의 근거와 가장 강한 반론을 확인하고, 원래 주장자가 반론에 답한다.
3. 인정된 문제와 남은 불확실성에 대응하는 C 후보를 만든다.
4. 비용과 이해관계자 손익, 실행 책임, 실패 조건을 대조한다.
5. 비판을 반영한 권고와 끝내 해결되지 않은 약점을 학생이 보고서에 사용할 수 있게 정리한다.

초반에 A와 B를 동일하게 옳은 입장으로 취급할 필요는 없다. A를 선택하게 되는 압박과 단기 유인을 가장 강하게 재구성하되, 확인된 사실을 왜곡하거나 부정을 정당화하도록 역할을 주지 않는다. 특정 처리의 기준 적합성은 실제 원문·사실관계를 확인할 때까지 별도 검증 대상으로 남긴다.

과제는 AI 오류 3건 이상을 요구하지만 사용자 지시는 오류를 꾸미지 말라는 것이다. 실제 확인된 오류가 부족하면 부족한 수와 검토 범위를 표시한다. 숫자를 맞추기 위해 오답을 만들거나 의심만 있는 항목을 확정 오류로 올리지 않는다. 과제에 나온 정량 철회 조건의 예시 역시 일반적인 법적 허용선으로 재사용하지 않는다.

## 5. 추가로 확인된 구조적 문제

| 현재 구조 | 보고서에 미칠 수 있는 영향 | 수정 |
| --- | --- | --- |
| 일반 JSON의 `conclusion` 설명이 매번 ‘최종 판단’(`:510`) | 1라운드 답변부터 최종형 문장을 작성하도록 지시한다. | `provisional_position`과 마지막 단계의 `decision`을 분리한다. |
| 연구 모드에는 교차 검증 뒤 전용 재반론이 없다(`:32–38`). 합의 모드에는 있다(`:42`). | 자신의 주장에 대한 반박을 처리하지 않고 C 설계로 넘어갈 수 있다. | 연구 모드에도 반론 응답 절차를 추가한다. |
| `execute()`는 응답이 저장되면 다음 순서로 이동한다(`:781–813`). | 발언 완료를 근거 검토 완료로 오인할 수 있다. | 실행 진행률과 검토 상태를 별도로 저장한다. |
| 독립 단계 이후 `peers=state['turns']`(`:651`) | 같은 단계 후순위 참가자만 앞선 참가자의 이번 단계 발언을 본다. | 단계 시작 시 공유 자료를 고정하고, 다음 단계에서 전원 결과를 공개한다. |
| `peer_context()`가 모든 발언·필드에 용량을 나눠 발췌한다(`:633–645`). | 기록이 길어질수록 특정 반박과 출처가 잘려 응답 누락이 발생할 수 있다. | 현재 검토할 주장·반박·출처를 우선 배정하고 생략 ID를 알린다. |
| `is_accounting_debate()`가 선택 자료 전체의 키워드로 판단한다(`:515–518`). | 이전 회계 자료가 남으면 다른 주제에도 PBL 지침이 적용될 수 있다. | 새 실행에서 사용자가 고른 분야를 저장한다. 키워드 판단은 기존 기록 호환용으로만 둔다. |
| UI가 초기 `proposals`까지 ‘채택’ 그룹에 표시한다(`web/app.js:264–269`). | 개별 의견이라는 설명이 있어도 초반 선택이 확정적으로 보일 수 있다. | 후보·검토 중·잠정 우선·최종 권고를 단계에 맞게 표시한다. |

현재 UI에는 이미 ‘잠정 결론’, ‘전체 결론 미완료’, ‘개별 AI 채택은 전체 합의가 아님’이라는 보호 문구가 있다. 이 부분을 없애거나 모든 요약을 잘못된 확정으로 취급하지 않는다. 첫 화면의 참가자 카드에는 판단의 잠정 상태를 더 직접적으로 붙인다.

## 6. 권장 연구 흐름: 5개 연구 단계 안의 7개 실행 절차

원래 연구 목적 5개는 유지한다. 교차 검증을 ‘반박 작성’과 ‘당사자 응답’으로 나누고, 교수 비판 뒤 수정 절차를 유지한다.

| 실행 순서 / ID | 수행할 일 | 허용할 결과 / 다음 단계에 넘길 것 |
| --- | --- | --- |
| 1. `independent` 독립 조사 | A/B의 근거와 손실, 네 쟁점, 반례, 입장을 바꿀 조건을 독립 작성 | 잠정 입장, 주장 ID, 미평가 C 씨앗. C 선정·전원 합의·최종 실행 권고는 하지 않는다. |
| 2. `cross` 교차 검증 | 다른 모든 참가자의 핵심 주장을 검토. 먼저 상대 주장을 정확히 재구성한 뒤 근거·수치·출처·논리를 비판 | 주장 ID에 연결된 반박, 동의 이유, 필요한 검증. 반박할 근거가 없으면 이유와 함께 수용한다. |
| 3. `rebuttal` 반론 응답 | 주장자가 자신에게 제기된 각 핵심 반박에 수용/부분 수용/기각으로 답변 | 수정 주장, 수정 이유, 검증된 오류와 단순 미확인 구분, 아직 답하지 못한 항목. |
| 4. `alternatives` C 설계·잠정 선택 | 독립 씨앗을 공개하고 현재 쟁점에 맞게 C 3~5개를 비교. A/B도 비교 기준으로 남김 | 해결할 문제·수단·비용·실행 조건·단점·가정, 후보 1+3 결합 검토, 잠정 우선안. 적합한 안이 없으면 선정 보류. |
| 5. `perspectives` 윤리·손익·실패 검토 | 세 윤리 관점과 관련 강의 이론, 이해관계자 단기/장기 손익, 민감도, 최악 시나리오 | 계산 입력·단위·산식·범위, 실패 조건별 관찰 지표·책임자·대응 행동. 우선안을 바꿀 수 있음. |
| 6. `professor` 교수 비판 | 근거 부족·논리 비약·실행 불가능성·반례를 우선 검토. 칭찬 금지 | 감점 이유와 수정 요구를 해당 주장·후보·계산 ID에 연결. 지적을 억지로 만들지 않음. |
| 7. `revision` 비판 반영·최종 판단 | 각 수정 요구의 처리 결과를 기록하고 C를 재선택하거나 권고 보류 | 조건부 권고, 채택·기각 이유, 소수의견, 남은 한계, 4페이지 보고서 목차와 부록 근거. |

`candidate_seeds`는 1단계 원본에 즉시 저장하지만 2·3단계의 다른 AI 입력에서는 제외한다. 교차 검토가 초기 해결책의 선호보다 사실·논거에 집중하도록 하기 위한 설계 선택이다. UI에서는 ‘미평가 아이디어’로 접어서 볼 수 있다. C 설계 단계에는 원본 ID와 함께 공개한다.

교수 비판 전에 C를 설계하는 이유는 실행 가능성과 실패 조건을 실제 후보에 대입해 검토하기 위해서다. 최종 라운드에서는 새 이름만 붙인 대안을 갑자기 채택하지 않는다. 그때 새로운 핵심 제약이나 전혀 새로운 후보가 나왔다면 ‘추가 검토 필요’로 남긴다.

## 7. 프롬프트·자료·역할 설계

### 공통 프롬프트

공통부에는 출처, 사실과 가정의 구분, 원문 인용, 개인 의견과 전원 합의의 구분, 실제 오류 기록, 자료 안의 명령 무시, 허용된 도구 범위만 둔다. C 설계·정량 철회 조건·최종 판단은 단계 지침으로 옮긴다.

독립 조사 지침의 핵심 문구는 다음과 같이 바꾼다.

> 지금은 독립 조사 단계다. A/B의 근거와 비용을 구분하고, 가장 설득력 있는 잠정 입장과 그것을 바꿀 증거를 제시하라. 가능한 C의 씨앗은 candidate_seeds에 미평가 가설로 기록하라. 후보를 채택하거나 전체의 최종 결론을 선언하지 마라. 근거가 부족하면 판단을 유보하라. proposals는 빈 배열이어도 된다.

교차 검증 지침에는 다음을 추가한다.

> 실제 주장 ID와 문구를 지목하라. 상대 주장에 대한 가장 강한 해석부터 적고 검증 가능한 반박을 제시하라. 동의하거나 오류가 확인되지 않은 경우에도 그 이유를 기록하라. 상대가 말하지 않은 극단적 입장을 만들어 반박하지 마라.

최종 판단 지침에는 다음을 추가한다.

> 최종 권고는 앞 단계에서 검토한 후보와 비판 처리 기록에 연결하라. 채택 불가능한 제약, 아직 확인하지 못한 근거, 수치 가정을 숨기지 마라. 자신의 의견과 다른 참가자의 명시적 동의를 구별하라. 다수결을 사실 확인의 증거로 사용하지 마라.

역할은 고정 찬반보다 검토 책임으로 나눈다. 예: 회계 근거·출처, 이해관계자 손익, 실행·유동성·일정, 반례·실패 조건. 어떤 모델이 어떤 역할을 맡을지는 기존 사용자 설정을 유지한다. 모든 AI는 상대의 핵심 주장 검토에 참여한다. AI별 전문성을 검증 없이 가정하지 않는다.

모더레이터를 선택한 경우에도 동일한 증거 기준을 적용한다. 1~3절차에서는 쟁점과 미응답 목록, 4~5절차에서는 후보 비교, 6~7절차에서는 비판 처리와 조건부 권고를 정리한다. 다른 AI를 대신해 동의를 선언하거나 전원 결론을 확정할 권한은 주지 않는다.

### 단계별로 같은 정보를 제공

각 단계 시작 시 공유할 이전 단계 결과의 ID 목록과 해시를 저장한다. 같은 단계의 모든 AI는 이 공통 목록을 사용한다. 역할별 추가 자료와 자기 답변 원문은 별도로 기록한다. 실행 자체는 기존처럼 순차 호출해도 된다. 새 병렬 실행이나 인증 공유 구조를 도입할 필요가 없다.

입력 용량이 부족할 때는 현재 답해야 할 주장·반박의 원문, 출처·계산, 미해결 목록을 우선한다. 모든 과거 결론을 같은 길이로 잘라 넣지 않는다. 필수 반박 원문이 용량 안에 들어가지 않으면 누락한 채 완료 처리하지 않고 자료 보완 상태로 남긴다. 자료의 표·숫자·주석은 문맥 없이 잘라 확정 근거로 사용하지 않는다.

### 일반 토론과 회계 연구 분리

새 실행에 `domain=accounting_pbl|general`을 명시하고 주제·자료의 키워드 추측을 기본으로 사용하지 않는다. 일반 토론의 공통 지침에서는 A/B/C와 회계 이론을 제거한다. 사용자가 준 실제 질문에 답하고, 정책·대안을 요구했을 때 별도 제안하도록 한다.

자유 라운드는 1회이면 독립 의견만, 2회이면 독립 의견과 상호 검토까지만 표시한다. 이 경우 충분한 연구·합의 완료라고 표시하지 않는다. 3회 이상에서도 반론이 해소되지 않았다면 마지막 발언이 자동으로 합의가 되지 않는다. 연결 확인용 테스트와 사용자가 선택하는 자유 토론은 UI 의미를 구분하되, 기존 저장된 `smoke` ID는 호환성을 위해 보존한다.

## 8. 데이터 계약과 진행 조건

아래 필드는 새 프로토콜용 제안이며 현재 구현에는 없다. 기존 `analysis`, `claims`, `audit`, `proposals`, `conclusion`, `unresolved`와 원본 응답은 보존한다.

| 필드 | 목적 |
| --- | --- |
| `provisional_position` | 현재 입장, 근거 주장 ID, 반증·변경 조건 |
| `candidate_seeds[]` | 독립 후보 ID, 아이디어, 확인해야 할 가정. 상태는 `unassessed` |
| `challenges[]` | 반박 ID, 대상 주장·발언 ID, 실제 인용, 반박 근거, 중요도와 이유 |
| `responses[]` | 반박 ID, 수용/부분 수용/기각/미응답, 수정 주장 ID, 근거 |
| `candidates[]` | 고정 ID, 해결할 쟁점, 출처가 연결된 비용·가정, 일정·책임자, 실행 제약, 결합 이력 |
| `decision` | `not_due|provisional|conditional_recommendation|withheld`, 후보 ID, 조건, 반대 이유 |
| `review_state` | 검토 대상 수, 응답 누락, 근거 확인 대기, 추가 검토 이유. 실행 성공 여부와 분리 |
| `phase_inputs` | 각 단계에서 사용한 공통 발언 ID·해시, 자료 버전, 생략된 항목 |

주장과 후보는 발언 접두어를 붙여 구분한다. 예: `S1A2.CLM1`, `S4A2.C1`. 후보 1+3 결합은 같은 후보 목록의 고정 ID로 기록한다. 서로 다른 AI의 ‘후보 1’을 같은 안으로 취급하지 않는다. 목록 간 결합은 양쪽 원본 ID를 명시한다. 1+3은 반드시 검토할 조합이지 선택 점수를 미리 높여 줄 조합이 아니다.

진행 조건은 다음처럼 적용한다.

1. 교차 검토 완료는 모든 다른 참가자의 핵심 주장에 검토 기록이 있다는 뜻이다. 단순 발언 수로 충족시키지 않는다. 중요한 회계·수치 주장에는 항목별 검토가 있어야 한다.
2. 재반론 완료는 각 핵심 반박에 답변 또는 미응답 사유가 연결되어 있다는 뜻이다. 미응답 사유가 있다고 문제가 해결된 것은 아니다.
3. 핵심 근거가 미확인이라도 가정을 공개한 조건부 후보 분석은 계속할 수 있다. 확인하지 못한 주장을 확정 근거로 승격하지 않는다.
4. 최종 단계에서 권고를 뒤집을 수 있는 미해결 반박·필수 근거 누락이 남으면 해당 권고는 `withheld`로 둔다. 수행한 분석과 부족한 자료를 그대로 제공한다.
5. 형식·참조 관계 오류는 로컬 검사로 표시한다. 자동으로 무제한 재질문하지 않는다. 추가 모델 호출이 필요하면 별도 보완 작업과 호출 수를 제시하고 사용자가 실행하게 한다.

코드가 자동 확인할 수 있는 것은 ID 존재, 인용 대응, 필수 필드, 응답 연결, 단계에 맞는 상태, 입력의 누락 여부다. 근거가 참인지, 반박이 충분히 해결됐는지는 코드만으로 입증할 수 없다. 모델의 ‘확인 완료’ 표시나 다른 모델의 동의는 독립 원문 확인을 대신하지 않는다. `web_checks`와 원문 위치, 확인 범위, 확인 주체를 별도로 유지한다.

`C안`이라는 단어를 금칙어로 검사하지 않는다. 문제는 해당 단어의 등장보다 비교·검증 전의 선정과 확정 권고다. 구조화된 상태를 검사하고 본문의 과도한 확정은 검토 경고로 남긴다. 본문을 몰래 고쳐 원래 답변처럼 저장하지 않는다.

## 9. UI와 산출물

첫 화면은 실행 진행률과 판단 상태를 나눠 보여준다. 예를 들어 ‘12/28 발언 완료 · 핵심 반박 2건 미응답 · 최종 판단 전’처럼 표시한다. 모든 호출이 끝나도 ‘전원 합의’나 ‘검증 완료’로 바꾸지 않는다.

분류별 요약은 다음 순서로 배치한다.

| 화면 | 표시할 내용 |
| --- | --- |
| AI별 독립 조사 | 잠정 입장, A/B 근거, 가정, 변경 조건, 접힌 미평가 후보 |
| 쟁점별 검토 | 원주장 → 실제 인용 → 반박 → 응답 → 남은 문제. 담당 AI·원문 링크 포함 |
| C 후보 비교 | 고정 후보 ID, 해결할 쟁점, 비용·가정, 윤리·일정·실패 위험, 결합·기각 이유 |
| 교수 검토 | 감점 요인, 수정 요구, 처리 결과, 해결되지 않은 지적 |
| 최종 판단 | AI별 조건부 권고 또는 보류, 명시적 일치 항목, 소수의견, 후속 확인 필요 자료 |

기존 산출물은 유지한다. `research_dossier.md`에는 근거와 이론, `alternatives_c.md`에는 씨앗→후보→수정 이력, `evidence_register.md`에는 주장별 확인 범위, `ai_audit.md`에는 실제 오류와 수정 질문을 기록한다. `debate_log.md`와 JSON은 원본으로 남긴다. `professor_review.md`는 비판과 처리 결과를 연결한다.

`report_outline.md`는 과제의 4페이지·5개 섹션 요구에 맞춰 구성한다. SCQA는 특히 1페이지 전략 메모에 적용하고, 나머지 본문에는 AI 감사·사회적 효용·회계 실질/C 계획·Pre-Mortem을 배치한다. 전체 증거표와 실제 대화는 부록으로 보낸다. 제출용 완성 문장을 자동 대필하기보다 각 주장에 사용할 근거와 남은 검증을 안내한다.

## 10. 최소 수정 순서와 호환성

| 순서 | 파일·위치 | 변경 범위 |
| --- | --- | --- |
| 1 | `debate.py`: BASE, 단계 지침, `build_prompt()` | 전역 C·최종 판단 제거, 단계별 출력 계약, 모더레이터 지침, 일반 질문 보존 |
| 2 | `debate.py`: `plan()` / `run_plan()` | 새 연구 실행에 `rebuttal` 추가. `protocol_version=3`에만 적용 |
| 3 | `debate.py`: context / normalize / execute | 단계 입력 고정, 주장·반박 연결, 검토 상태, 미확인·보류 처리 |
| 4 | `ui_server.py` 및 실행 생성 경로 | 분야·프로토콜·검토 상태 저장 및 반환. 구버전 상태의 읽기·재개 유지 |
| 5 | `web/app.js`, `web/index.html`, 필요 시 CSS | 잠정/최종·진행/검토 상태 분리, 주장→반박→응답 화면, 분야 선택 |
| 6 | `debate.py`: `render()` 및 오프라인 테스트 | 기존 Markdown/JSON 보존, 새 연결 정보 반영, 호환성·진행 조건 검증 |

현재 실제 페이지는 `/app.js`를 불러오며 서버 정적 경로에도 이 파일이 있다. `web/summary.js`만 바꾸고 실제 화면이 바뀌었다고 판단하면 안 된다. 중복 요약 코드를 유지할지 정리할지는 별도 검토하되, 이번 기능에 필요한 수정은 실제 로드 경로에 적용한다.

기존 연구·합의·자유 토론은 저장된 프로토콜과 단계 ID를 사용한다. 중간에 새 재반론을 끼워 넣어 완료 발언을 다른 단계로 재해석하지 않는다. 구버전 기록에서 새로운 연결 데이터가 없으면 ‘기록 없음’으로 표시한다. 기존 답변을 새 스키마로 재생성하거나 결과를 소급 확정하지 않는다.

공식 CLI 호출·로그인 재사용·로컬 저장·중단과 재개·읽기 전용 기본값·웹 검색 선택 기능은 유지한다. 모델과 추론 강도는 변경하지 않는다. 새 유료 API나 프록시는 필요 없다.

## 11. 호출 수와 검증 계획

현재 연구는 내부 6절차이므로 4명이면 기본 24회 호출이다. 권장안은 7절차 × 4명 = 28회로, 재반론 4회가 늘어난다. 호출 횟수 기준 약 16.7% 증가이며 토큰·대기 시간·구독 한도 소모가 같은 비율로 늘어난다는 뜻은 아니다. 3명이면 21회, 5명이면 35회다. 별도 유료 API 경로를 추가하지 않지만 각 서비스의 구독 사용량은 소비한다. 추가 검증 반복을 자동 무한 실행하지 않는다.

향후 구현 시 우선 통과해야 할 오프라인 검증:

- 독립 조사에 다른 AI 발언이 들어가지 않고, 같은 단계의 공통 입력 ID가 실행 순서에 따라 달라지지 않는다.
- 일반 토론에서 C와 회계 이론을 강제하지 않으며, 초기 응답의 빈 `proposals`가 허용된다.
- 초기 후보와 최종 선정이 별도 상태로 저장되고, 최종 단계 전에는 최종 권고 상태를 허용하지 않는다.
- 핵심 반박의 응답 누락과 미확인 근거가 검토 상태에 남고, 전체 호출 성공만으로 최종 결론이 확정되지 않는다.
- 중단·재개 후 단계 입력과 완료 발언 ID가 유지되며, 구버전 실행은 이전 순서로 재개된다.
- 사용자 정의 역할, 선택 자료, 모델 설정, 기존 JSON/Markdown 출력, 출처 확인 기록을 보존한다.
- 기존 비밀정보 마스킹·공식 CLI 제한·유료 API 환경 차단 회귀 검사를 유지한다.
- 실제 제공되는 `app.js`로 UI 계약 테스트를 하고, 화면에서 원주장→반박→응답 연결과 잠정/최종 표시를 확인한다.

효과 검증은 사용자가 실제 토론을 허용한 뒤에만 수행한다. 동일 사례·모델·역할·자료를 고정하고, 기존/새 프로토콜에서 초기 확정 권고, 핵심 반박 응답 누락, 원문 출처 확인 가능성, 근거에 따른 입장 변경, C의 쟁점 해결 범위를 비교한다. 단순한 C 단어 수·갈등 강도·입장 변경 건수를 품질 점수로 쓰지 않는다. 한 번의 실행 결과를 모든 모델에 대한 일반 결론으로 제시하지 않는다.

이번 검토의 산출물은 이 수정 설계다. 현재 서비스의 동작은 그대로이며 새 프로토콜은 아직 적용되지 않았다.

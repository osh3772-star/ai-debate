# ‘교수 관점 적대적 비판’ 단계의 목적과 타당성 검토

검토일: 2026-10-21. 대상: 현재 v3 코드, 제공된 PBL 과제·평가표, 관련 논문 본문의 방법·결과·한계.

후속 상태: 사용자 승인 후 새 연구에 적용하는 검토 정책 1을 구현했다. 현재 적용·검증 결과는 [구현 기록](final_review_validation.md)을 참조한다. 아래는 구현 전 조사 당시의 판단과 개선안을 보존한 내용이다.

이번 작업은 코드 검토와 문헌 조사다. 실행 코드·설정은 변경하지 않았으며, 실제 AI 토론·모델 호출이나 서버 재시작을 하지 않았다. 아래 개선안과 검증 항목은 아직 구현·실험 결과가 아니다.

**판단: 최종 검토 단계는 유지할 이유가 있다. 다만 ‘적대적 비판·칭찬 금지’는 ‘평가 기준에 따른 근거·반례 검토’로 수정하는 편이 타당하다. 검토 결과에는 ‘검토 범위 내 중대한 결함 없음·원안 유지’가 반드시 포함되어야 한다.**

## 1. 왜 들어갔는가

최초 사용자 요청의 5단계에 ‘교수 관점 적대적 비판’, ‘칭찬을 금지’, ‘반례와 가능한 경우 독립 검증’, ‘수정 후 남은 약점·소수의견 보존’이 명시되어 있었다. 현재 이름과 지침은 이 요구를 구현한 것이다. 이것을 교수자가 직접 지정한 절차나 연구로 효과가 입증된 교수 페르소나라고 설명해서는 안 된다.

제공된 `(PBL)7주차_중간PBL과제.md`의 141–152행은 Steelman Pre-Mortem과 정량적 Kill Conditions를 요구한다. 167행 이후 평가표는 장기 효용, 회계 메커니즘, AI 감사, 독립성, C안 실행 등을 평가한다. 따라서 구체적인 C안을 만든 뒤 반례·실패 조건·근거 누락을 점검하는 목적은 과제와 맞는다. 다만 해당 자료에서 ‘교수 역할 AI가 반드시 흠을 찾아야 한다’거나 ‘타당한 논거를 인정하면 안 된다’는 요구는 확인되지 않았다.

현재 v3 연구 모드는 C 후보 비교와 윤리·실패 검토 뒤에 이 단계를 두고, 그 다음에 수정·최종 판단을 수행한다. 최종 선택 전에 약점을 살펴볼 기회라는 위치는 적절하다. 교수라는 호칭 자체가 검토자의 권위나 채점 정확성을 보장하지는 않는다.

## 2. 완성도 높은 안도 억지 비판을 받는가

**가능성은 있다. 그러나 현재 코드가 반드시 비판을 만들도록 강제한다는 설명도 정확하지 않다.**

| 현재 코드에서 확인한 사실 | 의미 |
| --- | --- |
| `research_protocol.py:46`은 ‘칭찬 금지’와 오류·비약·실행 불가능성 검토를 지시한다. 동시에 ‘오류를 억지로 만들지 마라’고 명시한다. | 결함 탐색에 치우칠 가능성이 있는 지시와 허위 비판 방지 지시가 함께 있다. 실제 영향의 크기는 현재 모델로 측정하지 않았다. |
| `base_prompt()`는 빈 배열을 허용하고, 빈칸을 채우기 위한 반박을 금지한다. | 비판을 최소 몇 건 채워야 한다는 요구는 없다. |
| `contract()`의 검토 판정에는 `supports`, `challenge`, `unverified`가 있다. | 타당한 주장을 지지하거나 확인 불가로 남길 수 있다. ‘칭찬 금지’와 근거 있는 지지의 관계를 더 명확히 해야 한다. |
| 최종 단계는 비판의 수용·부분 수용·기각을 허용한다. `review()`도 이유 있는 `기각`과 `addressed` 응답을 처리한다. | 교수 비판이라고 무조건 수정할 의무는 없다. |
| `review()`는 대상 ID·실제 문구·응답 연결 등을 검사한다. | 근거의 내용이 참인지, 반례가 성립하는지, 기각 이유가 합당한지는 자동으로 판정하지 못한다. |
| `critical`인 미응답 지적은 최종 권고를 보류시킨다. | 부당한 비판도 형식 요건을 갖추면 보류 사유가 될 수 있다. 반대로 부실한 기각도 형식을 충족하면 해결 처리될 수 있다. |
| 앞선 토론에 참가했던 동일 AI들이 교수 검토 단계에도 참여한다. | 별도의 독립 교수 심사와 같지 않다. 다른 AI의 안을 검토하도록 제한하지만 앞선 논의와 입장의 영향을 받을 수 있다. |

‘칭찬 금지’만으로 억지 비판 발생을 단정할 수는 없다. 더 중요한 구조적 한계는 **비판도 오류를 포함할 수 있는데, 비판의 타당성을 사실로 확정할 독립 절차가 없다는 점**이다. 빈 지적 목록도 ‘충분히 검토하고 결함을 찾지 못함’과 ‘검토가 누락됨’을 명시적으로 구분하기 어렵다.

이 시스템의 현재 교수 검토에서 실제로 억지 비판이 발생했다는 실험 결과는 이번에 확보하지 않았다. 이전 실행·모의 테스트를 그 증거로 사용하지 않았다.

## 3. 관련 연구가 뒷받침하는 범위

아래는 논문 검색 초록뿐 아니라 관련 본문을 확인한 내용이다. 수학·객관식·코드·문장 생성 과제에서 얻은 결과를 회계윤리 보고서의 성적 향상이나 현재 모델 조합의 오류율로 환산할 수는 없다.

| 연구와 읽은 부분 | 확인한 결과 | 이 설계에 대한 함의와 한계 |
| --- | --- | --- |
| Huang 외, *Large Language Models Cannot Self-Correct Reasoning Yet*, arXiv v2(2024), §3.3·표 4–6·§5–7. [본문](https://arxiv.org/html/2310.01798v2) | 외부 피드백 없는 추론 수정에서 정답을 오답으로 바꾸는 사례와 성능 저하를 보고했다. 중립적으로 정오를 검토하게 하는 문구에서도 문제가 남았다. | ‘비판하고 다시 쓰면 개선된다’는 보장은 없다. 당시 GPT-3.5/4 계열·Llama-2 등의 결과이며, 현 시스템의 피해율을 측정한 것은 아니다. |
| Gou 외, *CRITIC*, ICLR 2024, arXiv v4, 알고리즘 1·§4.4·부록 A. [논문](https://arxiv.org/abs/2305.11738) | 검색·코드 실행 등 외부 도구 피드백으로 검증한 후 수정하는 방식의 개선을 보고했다. 알고리즘에는 현재 답이 맞다고 판단되면 수정 없이 반환하는 종료 조건이 있다. | 근거 확인과 수정 중단 경로를 설계할 근거다. 도구를 썼다는 사실만으로 출처 해석과 검토가 모두 정확해지는 것은 아니다. |
| Madaan 외, *Self-Refine*, 2023년 연구, 검색 인덱스 갱신일 2023-05-29 원고의 §2–4. [논문](https://arxiv.org/abs/2303.17651) | 구체적이고 실행 가능한 피드백의 이점을 보고했다. 개선 불필요 시 종료할 수 있고, 반복 중 일부 품질 차원이 나빠지는 경우도 기술한다. | 후속 검토를 전부 없앨 근거는 없다. 포괄적인 흠잡기보다 대상·이유·수정 방법이 분명한 피드백이 적합하다. |
| Zheng 외, *When “A Helpful Assistant” Is Not Really Helpful*, arXiv v3(2024), §3·§7–9. [본문](https://arxiv.org/html/2311.10054v3) | 162개 역할과 2,410개 사실 질문을 다룬 실험에서 역할 부여가 일반적인 정확도 개선을 보장하지 않았고, 효과가 질문·모델별로 달랐다. | ‘교수’라는 역할명만으로 검토 전문성을 인정할 수 없다. 특정 역할이 특정 상황에서 도움이 될 가능성까지 부정한 결과는 아니다. |
| Basil 외, *Prompting Science Report 4*, 2025년 공개 연구보고서, 인덱스 갱신일 2025-12-08 원고의 Results·Discussion. [논문](https://arxiv.org/abs/2512.05858) | 6개 모델과 GPQA Diamond·MMLU-Pro에서 전문가 역할의 일관된 정확도 이득을 찾지 못했다. Gemini 2.0 Flash 등 조건별 예외도 보고했다. | 교수 페르소나의 효과는 별도로 검증해야 한다. 학술 객관식 결과이며 이 과제의 주관식 심사를 직접 평가한 연구가 아니다. |

반대 결과도 확인했다. Mullens·Shen의 2026년 프리프린트는 전문가 역할의 이득과 기존 실험 설계 문제를 주장한다. 읽은 §4.9는 핵심 분석의 작은 화학 문제 표본과 단일 모델, 제한된 일반화 가능성을 명시한다. 이 연구를 근거로 역할 프롬프트의 효과가 전혀 없다고 단정하지 않는다. 반대로 이 결과도 ‘교수 역할이 회계윤리 심사의 정확성을 보장한다’는 근거는 아니다. [논문](https://arxiv.org/abs/2603.20225)

자기수정의 긍정·부정 연구는 과제, 피드백, 평가 방식이 다르다. 특히 외부 정답을 이용해 이미 맞는 답을 수정하지 않도록 하는 실험과, 모델 스스로 정오를 판단해야 하는 실제 운영을 구분해야 한다. 본 시스템에서는 사후 모델 합의나 형식 검사를 정답 판정기로 취급하지 않는다.

## 4. 권장하는 검토 기준

단계 이름은 ‘평가 기준 기반 최종 검토’로 바꾸는 것을 권장한다. 역할은 원안을 공격하는 것이 아니라, 주장과 비판 양쪽의 입증 책임을 확인하는 것이다.

| 검토 결과 | 처리 |
| --- | --- |
| 확인된 결함 | 실제 문구, 충돌하는 자료·계산·평가 기준, 결론에 미치는 영향을 연결하고 수정을 요구한다. |
| 확인이 필요한 전제 | 무엇이 미확인인지와 확인 방법을 기록한다. 미확인을 곧바로 오류로 기록하지 않는다. 핵심 전제가 미확인이면 조건부 판단 또는 보류한다. |
| 조건부 위험 | 어떤 조건에서 실패하는지, 기존 대응으로 처리되는지 검토한다. 단지 실패 가능성이 존재한다는 이유만으로 안 전체를 기각하지 않는다. |
| 선호·표현 제안 | 선택 사항으로 표시한다. 제공된 평가 기준과 연결되지 않으면 확정 감점 사유로 쓰지 않는다. |
| 중대한 결함 없음 | 확인한 범위·자료와 원안 유지 이유를 기록하고 통과시킨다. 완벽함의 증명이나 실제 교수의 점수 보장으로 표현하지 않는다. |

설명용 가상 예시이며 실제 AI 오류 로그가 아니다. 어떤 실행안이 가용 자원 12, 비용 8, 최소 잔여량 3을 전제로 하고 산식 `12 - 8 = 4 ≥ 3`을 제시했다고 하자. 검토자가 별도 근거 없이 ‘자원 부족으로 실행 불가능’이라고 지적하면 기각해야 한다. ‘비용이 10으로 증가하면 잔여량 2로 기준 미달’이라는 지적은 조건부 위험이다. 그 가능성과 대응이 이미 적절히 다뤄졌다면 중복 결함으로 셀 필요가 없다. 수치의 출처가 없다면 그 부분은 전제 확인 과제로 남긴다.

## 5. 제안하는 단계 지침 — 아직 미적용

> 제공된 과제·평가 기준에 따라 결론, 핵심 근거와 실행안을 검토하라. 먼저 주장을 가장 강하고 정확한 형태로 재구성하라. 결함이 있다고 전제하지 말고, 통과한 근거와 유지할 요소도 기록하라. 의례적인 칭찬은 생략하되 타당성 인정은 허용한다.
>
> 지적마다 대상 ID·실제 문구·관련 평가 기준·근거 또는 성립하는 반례·결론에 미치는 영향을 제시하라. 확인된 오류, 미확인 전제, 조건부 위험, 선택적인 표현 제안을 구분하라. 반례는 원안의 가정과 적용 범위를 존중하며, 가정을 바꾸었다면 그 조건을 명시하라.
>
> 지적의 최소 개수는 없다. 중대한 결함을 찾지 못하면 검토 범위와 원안 유지 이유를 기록하고 종료하라. 뒷받침할 근거가 없는 비판은 기각하거나 확인 필요로 남겨라. AI 다수의 동의, 비판적 말투, 교수 역할명만으로 비판을 사실로 확정하지 마라. 수정 후에는 수정 이유를 해결했는지와 새로운 모순이 생겼는지를 확인하라.

최종 응답 단계 역시 ‘비판 반영’만 강조하지 않고 ‘비판의 채택·기각과 최종 판단’으로 설명하는 편이 맞다. 수용한 비판만 변경으로 연결하고, 기각한 비판과 원안 유지 근거를 보존한다.

## 6. 구현 시 필요한 최소 변경과 검증

1. 단계 지침과 UI 설명을 함께 바꾼다. 이름만 바꾸고 ‘감점 사유·수정 요구’를 계속 필수 산출물처럼 표시하지 않는다. 기존 로그와 내부 단계 ID는 보존할 수 있다.
2. 검토 범위와 결과를 명시하는 필드를 둔다. 빈 `challenges`만으로 통과시키지 말고 ‘무엇을 확인했고 왜 유지하는지’를 기록한다. 단, 모델의 통과 보고 자체를 독립 검증 완료로 표시하지 않는다.
3. 결함을 주장하는 쪽에도 근거를 요구한다. `critical`이라는 모델 표시 하나를 확정 판결로 취급하지 않는다. 중대한 미확인 문제는 최종 판단을 보류하되, 부당한 지적을 이유 있게 기각할 경로도 유지한다.
4. 원문 확인·계산·과제 조건으로 반례와 기각 사유를 대조한다. 웹 원문을 볼 수 없으면 확인 범위를 표시한다. 새 쟁점이 없으면 같은 비판을 반복하지 않는다.
5. 검증에는 ‘정확하고 충분한 안’, ‘확인 가능한 오류가 있는 안’, ‘미확인 전제가 있는 안’, ‘틀린 비판을 받은 안’을 함께 사용한다. 실제 결함 탐지율뿐 아니라 허위 비판 비율, 맞는 내용을 잘못 수정한 비율, 근거 있는 기각 보존 여부를 확인한다.

형식 테스트만으로 비판의 질을 증명할 수 없다. 실제 모델 평가를 한다면 사람이 평가 기준과 원자료로 판정한 비교 자료가 필요하다. 추가 AI 호출을 하는 실험은 사용자가 실행을 승인할 때 수행한다. 현재는 이 설계를 권고하는 단계다.
